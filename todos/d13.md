## 🔧 Implementation details

### Migration 012
```sql
CREATE TABLE IF NOT EXISTS notifications (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT NOT NULL,
  type VARCHAR(50) NOT NULL,
  message VARCHAR(500) NOT NULL,
  link VARCHAR(255) NULL,
  is_read TINYINT(1) NOT NULL DEFAULT 0,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_notif_user (user_id, is_read)
);
```

### Triggers (proposed recipients)
- Admin **approve/reject/cancel** a booking → notify the **booking's employee**.
- Driver **confirm/decline/complete/no_show** → notify the **employee** (and optionally the admin).
- **3rd no-show block** → notify the **employee** ("booking blocked until …").
- New booking submitted → optional: notify **admins** ("new booking pending"). (Decide whether to fan-out to all admins.)
- Implement as a small `notify(userId, type, message, link)` helper called from the existing controllers; keep it best-effort (don't fail the main action if a notification insert fails).

### Backend endpoints (`requireAuth`, own-scoped)
- `GET /notifications` → recent for `req.user`; include `unread` count (or a separate `GET /notifications/unread-count`).
- `PATCH /notifications/:id/read`; `POST /notifications/read-all`.

### Frontend
- A `NotificationBell` component in each layout header: badge with unread count, dropdown of recent, link to the page.
- `pages/Notifications.jsx` (replace stub): list with read/unread styling + "Mark all read".
- Poll unread count every ~30s via `setInterval` (clear on unmount; skip when `document.hidden`).

### Notes
- Keep it simple: no real-time push. Polling + refetch-on-navigation is enough for internal use.
- Reuse the status color palette for notification type accents if useful.
